# Shared-Source Ownership

Use this instruction only for work that is about to modify shared source or needs the shared tree to remain stable. Read-only inspection and verified writes to the selected item's own artifacts do not acquire source ownership.

## Preflight, Resolve, and Reserve

- Resolve exactly one Feature, QUICK, or BUG from the current invocation or selected conversation. Feature uses its unique Scope brief's exact `feature_directory`; QUICK uses its exact Q ID and unique authoritative record; BUG uses the exact `.specify/bugs/<slug>` with an existing upstream `assessment.md`. Never infer identity from repository membership, branch, title, recency, or `.specify/feature.json`.
- Complete read-only and item-local preparation first. For the canonical exact-identity, readiness, current-source, stale-routing, surface-derivation, and preview procedure, load and follow `.github/skills/speckit-preflight/SKILL.md`. This is automatic immediately before shared-source mutation; a standalone result is never reused. Do not maintain a second definition of Preflight semantics here.
- Immediately before implementation, reserve once using `node .github/hooks/speckit-source-ownership.mjs claim` with exactly one identity option (`--feature-dir <directory>`, `--quick-id <Q###>`, or `--bug-dir .specify/bugs/<slug>`) and repeated `--path <workspace-relative-path>` / `--resource <canonical-id>` options for the complete surface. No empty surface or token is accepted.
- The canonical Preflight's read-only `preview` is advisory; the atomic `claim` is the final conflict check and reservation. Only a successful claim means `ADMITTED TO IMPLEMENT`. Missing or ambiguous targets, conflict, or unknown state stop the whole item before source changes.
- The helper atomically compares the complete incoming item with every current reservation. Any exact or ancestor/descendant path overlap, or exact shared-resource overlap, rejects the entire incoming item; it is never partially admitted. Complete disjoint surfaces may proceed concurrently. A fresh duplicate entry for the same item is blocked even if its submitted paths differ.
- A continuation may skip admission only when the current conversation directly shows it acquired the still-active reservation; item identity alone is not evidence. Unknown registry/surface state blocks admission. Version 1/2 single-owner records have unknown surfaces and globally conflict until exact release/recovery.
- After successful admission, continue normally through edits, tests, and validation without further ownership checks or transient tokens, including per-edit checks. Do not call `status`, `preview`, `claim`, or `revise` before ordinary edits/tool calls.
- If implementation discovers a material expansion outside the reservation, stop before changing the new area and call `revise` once with the complete updated surface. The helper atomically compares against every other reservation; on conflict, preserve the original reservation and stop only the expansion until the user resolves it. Ordinary work inside the current surface continues without checks.
- A blocked item does not partially implement or automatically resume when a conflict clears. A fresh explicit invocation repeats readiness and current-source Preflight before a new atomic claim.

## Retain, Release, and Recover

- Retain the reservation while source edits are active, while validation requires a stable implementation surface, or while accepted source-changing remediation remains, regardless of finding severity.
- `IMPLEMENTATION COMPLETE` means no currently known accepted work requires source modification or a stable implementation surface. It is not overall Feature/Quick/Bug completion. When strong evidence establishes this boundary, the authoritative implementation workflow must invoke the helper's `release` operation once with the exact owning identity (`--feature-dir`, `--quick-id`, or `--bug-dir`) and report the result. Review PASS is sufficient but not universally required. Do not infer completion from checked Tasks, Summary existence, finding severity, or overall item completion alone.
- When source requirements remain uncertain, retain the reservation and explain why. `/speckit-release <exact-item>` is the explicit user-controlled release action. Use it only at a stable implementation boundary, never during source edits or validation requiring a stable surface. Before release, give one concise warning that overlapping work may proceed and later remediation may wait; the explicit command is the user's action, so do not start an approval loop. Release changes only the matching registry reservation and MUST NOT edit work-item status, Tasks, Review findings, validation, or Summary.
- Release only the exact work item; preserve all other reservations. After release, later source remediation builds a new complete surface and runs ordinary admission against all current reservations; no historical priority applies.
- Never infer staleness from elapsed time or a closed conversation. Use `recover` only after the user explicitly inspects and accepts genuine abandonment/conflict. For readable registries, recovery may replace only the exact abandoned reservation, then must pass ordinary overlap admission. For malformed/unreadable/unsupported state, use `--confirm-inspected --confirm-discard-all` only after the user accepts that every unreadable reservation is abandoned. Recovery never implies implementation or item completion.
- An existing operation lock, malformed registry, unsupported version, unreadable path, or unsafe filesystem behavior is `UNKNOWN` and fails closed. Never remove a lock or overwrite reservations as routine cleanup.

## Stage Boundaries

- Implement, Quick, and upstream Bug Fix use the canonical Preflight skill and one-time complete-surface admission, with their own authoritative artifacts. In a Quick batch, resolve and admit each exact Q independently; disjoint Q items may proceed while only conflicting whole Q items are blocked. Do not create a batch-wide reservation or queue. Auto delegates to the authoritative implementation stage and must not reserve separately, bypass failure, or resume a blocked item automatically.
- Review remains read-only. It may inspect ownership status and must disclose attribution ambiguity; it never changes or releases ownership.
- Converge retains its existing upstream behavior and inputs. Do not claim that it consumes Git diff provenance or alter its responsibilities.
- Status applies the canonical Preflight readiness and compatibility vocabulary while reporting evidence read-only. It may use helper `preview` for an exact identity and complete candidate surface; the result remains advisory and never establishes admission. The registry coordinates BSK work-item transitions in one shared local working tree; it is not filesystem-level locking and does not prevent manual edits, external tools, non-cooperating sessions, or changes in separate/synchronized working trees. Do not claim supported-agent concurrency until the required two-session acceptance has actually run.
